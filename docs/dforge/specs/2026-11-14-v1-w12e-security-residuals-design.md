## Decisions

Quoted answers of the owner: "fix them" (the six findings the re-review left open, and the threat-model sentences they make inaccurate); "Full dforge flow (Recommended)" (the process question, 2026-11-14). The approach choices below are this session's recommendations after the architecture critic's round (`.dforge/critic-2026-11-14-v1-w12e-security-residuals-design-report.md`), put to the owner at the spec review. At the spec review (2026-11-14) the owner chose "Reload after join (Recommended)" for row 176 (U1), "Verify after join (Recommended)" for row 142 (U2), "Accept the refusal (Recommended)" for A9 (U3), and "Approve, keep the normal stops".

- **D1, residual A (row 176): reload nginx after NPM joins a network (owner, U1 (a)).** nginx resolves a custom location's static `proxy_pass` when it loads its configuration and keeps the answers while the name has none, or has moved; it also re-resolves at times no Darkpanel write marks (NPM's own reload every 6 hours, `npm.certificate.request`, every start of nginx), so the premise of `forwardTargets` (`internal/modules/npm/network_claims.go:823-826`) that a name with no answer "can reach NPM only after it is re-pointed" is false, and no record kept by the agent holds what nginx holds (Fable F2). Instead, once NPM holds its address there, nothing nginx resolved earlier matters: no container alias can answer an address NPM holds, so a reload after the join resolves every static name away from NPM. `npm.network.attach` and the undo of a detach keep today's check before the connect, then connect, read the address NPM took on the network (`networkEndpointOf`), refuse when it is a current forward target (an Engine-chosen address the pre-check could not predict), and make NPM reload nginx through its API, requiring the reload to be confirmed. A refused address or an unconfirmed reload disconnects NPM from the network again and fails with the Definite `npm.reserved`, with nothing left changed. With no proxy host there is nothing to reload and the reload is skipped. Which call of the pinned API reloads nginx without side effects, and how NPM reports a failed `nginx -t`, is unknown; the plan's NPM task settles it from the pinned image (candidates: a no-change save of one proxy host, re-saving the default-site setting) before D1 is built. Cost: a join is refused while nginx cannot reload because a static name has no answer; NPM then refuses every host write too, so `panel.exposure.add` could not finish anyway. Residual: between the connect and the confirmed reload (seconds, at a time the caller chose) nginx may still forward to the address NPM now holds; the threat model lists it beside D7. No table and no migration. Rejected: the recorded-addresses table of round 1 (Fable F2: unsound without stopping NPM's own reload, which NPM 2.16 may not allow); refusing a join while a name has no answer (the critic's High); restarting NPM so nginx re-resolves (it interrupts every proxied site).
- **D2, residual B (row 177): check the undo of a finished upgrade.** `Inverse` of `npm.instance.upgrade` in phase `done` runs a forward check before `rollback` and `restore`, on what `restore` recreates: the networks and static addresses of the upgrade row's `Config` (`instance_upgrade.go:181-207,683-689`) and `darkpanel-npm`, with the upgraded container's addresses counted as free. The reason of ruling W12a-R1, that a refusing rollback would leave NPM down, holds for the rollback of a failed upgrade and for recovery, which stay unchecked; it does not hold for a requested undo of a finished upgrade. `Inverse` in phase `done` runs `checkArchives`, then makes the original image available (the pull at `instance_upgrade.go:667`), then the forward check, then `rollback` (R7: a check before the pull leaves a window a caller can stretch by removing the unused original image). The check refuses, Definite and with nothing changed, when a network of `u.Config` no longer exists (R8: today that undo removes the upgraded container at `:671` and fails at `connect`, `:689`, leaving NPM down). When NPM's API does not answer, the undo is refused with `npm.unhealthy`, as the upgrade's own check is (`:115-119`, `network_claims.go:980-981`): a finished upgrade whose API stops answering cannot be undone until NPM answers again (R9).
- **D3, residual C (row 142): verify the addresses NPM holds after every start Darkpanel makes (owner, U2 (a)).** The upgrade keeps a second forward check after the pull (`instance_upgrade.go:220-222`) and before the effect is journaled (`:227`) and the container stopped (`:302`), returning the Definite `npm.reserved` itself, so a conflict visible then costs no downtime (R10; it cannot run after the stop, because `forwardCheck` lists proxy hosts through NPM's API, which the stopped container no longer serves). That check narrows the window but cannot close it: a caller who polls the NPM container's state can free a forwarded address between the stop and the new start (Fable F4). So every start of an NPM container Darkpanel makes then verifies what the container holds: the upgrade's recreate, `restore` (the undo of a finished upgrade, the rollback of a failed one, recovery from `recreating` and `waiting`), and `resume`/`recoverOriginal`, which restart the original. Immediately after the start, before waiting for the API, it inspects the container's addresses on every network and compares them with the forward targets read at the last check before the stop. Proxy hosts cannot change in between, because the upgrade holds the `npm` key (`instance_upgrade.go:60`, `proxyhost_add.go:50`). The targets are taken together with the agent's own fresh answers for the forwarded names, which need no NPM API. A held address that is a target is disconnected from its network at once, and the start fails with `npm.reserved` naming the proxy host, the address and the network. In the upgrade that failure rolls back to the original, whose `restore` runs the same verification, so the original comes back up without that network. `fail` must keep the `npm.reserved` code, which `notDefinite` strips today (`:283-288`). A start with no recorded target list (a restart of the original during recovery after an agent restart) reads the targets through NPM's API once the container answers, and disconnects on a hit then. Residual: the seconds between the start and the inspection, at a time Darkpanel chose. Rejected: a `docker` lock key (the critic's High); accepting the stop-to-start window (owner chose to close it).
- **D4, row 6: the guard builds the IPv6 leg of a `[::]` binding on a link-local-only host.** Only `npmPublicFlows` (`internal/modules/firewall/guard/flows.go:408`, the exclusion at `:421`) stops excluding link-local addresses; `wildcardDsts` (`guard/route.go:248`) is not changed, because it already keeps the reply route's preferred address (`route.go:249`), a link-local one on such a host, and excludes only the other link-local addresses (`:256`). The flow is `standIn`, so a cell whose reply has no route is skipped. The link-local leg is probed at the one address the reply route prefers, on every interface, so a rule keyed on another interface's link-local destination address is not seen (R19). On a link-local-only host that has an IPv6 default route (from router advertisements) the `2000::/3` cells have a reply route, so the refusal of A9 reaches every client of the exposure, not only a hidden one (R16, Fable F8). Rejected: also dropping the exclusion in `wildcardDsts` (the critic's High: it changes every IPv6 wildcard flow on every host and probes the link-local addresses of `docker0` and every veth, which security rows 27 and 28 left out on purpose); an `unknown` flow, which would refuse every guarded change on every IPv4-only host.
- **D5, row 178: the Tailscale link guard protects the visible client of an NPM exposure.** For a request through an exposure whose client is not a host address, the guard adds the client's flow to each public binding, as `linkListenFor` does for a direct client. A client that is a host address (a tailnet client that Docker's userland proxy carries) is the hidden client; it gets no flow, and the threat model names that case as a residual, recorded as a new low register row. The added flow applies only to `Via.Kind == "npm"`, carries the request mark, and mirrors `linkguard.go:186-192` with `linkListenFor` (`:351-364`); the stale comment at `:179` is corrected. The new row says that every IPv6 tailnet client is hidden while NPM's networks are IPv4 only (`flows.go:307-310`), which is the usual path for a MagicDNS name, not a corner case (R17). Rejected for now: a stand-in tailnet flow per binding for the hidden client, which needs its own design in `linkguard.go`.
- **D6, row 179: cut the forward host at its first `/` in `checkRestoredLocation`** (`internal/modules/npm/proxyhost_edit.go:241`), before the empty and `$` tests at `:242`, as `forwardTargets` does (`network_claims.go:854-862`); a cut placed after them leaves `<NPM address>/$request_uri` unchecked (R18).
- **D7: the accepted DNS risk stays.** A caller who controls a DNS name that nginx's resolver answers differently from the agent's can still publish NPM's own API (Known residual risks, `forward host`); D1 to D3 close the paths that need no such name, short of the seconds-long windows D1 and D3 state,, including a Docker alias the caller controls. The threat model says so next to each fix.
- **D8: no harness change.** The fixes are guard and lifecycle logic covered by unit tests; D4's tests are built from route answers and addresses captured read-only from real hosts (`ip -6 addr`, `ip -6 route` and the `netstat.RouteGet` lookups of R14) rather than written by hand; gate 7 reruns on the merge.
- Early CI: none. The CI configuration has no platform this host does not cover (`ci.yml` on the self-hosted Linux runner, `harness.yml` on ubuntu-24.04), and D8 adds no harness step.

Finish: merge

## Riskiest assumption

On an IPv4-only host (IPv6 addresses link-local only, no IPv6 default route), the one-line change of D4 does not make the guard refuse its ordinary changes: the global-source cells of the `[::]` leg have no reply route and are skipped by `standIn`, and only link-local sources are evaluated. Evidence: `standIn` skips a wild source in a cell of a route without a path that no reply reaches (`internal/modules/firewall/guard/flows.go:65`, `route.go:121`); how the kernel answers a route lookup for a link-local source with no output interface is unverified — the plan's first task captures, read-only from a real IPv4-only Docker host (this host, if it is one), `ip -6 addr`, `ip -6 route` and the agent's own `netstat.RouteGet` answers for the lookups that decide the skip: a `2000::/3` address with no source (`route.go:119`), the same from each local link-local address and from `::1` (`noReplyFrom`, `route.go:227-241`), an `fe80::/64` address with no source, and the same from the address that answer prefers (`route.go:160-164`) (R14). D4 is built only if the global lookups answer ENETUNREACH, EHOSTUNREACH or EACCES (`netstat/routes.go:104`); any other errno makes the flow unknown and refuses every guarded change through the exposure. If wrong, D4 fails closed on every IPv4-only host, and A9's question widens to every guarded change.
