## Decisions

Quoted answers of the owner: "fix them" (the six findings the re-review left open, and the threat-model sentences they make inaccurate); "Full dforge flow (Recommended)" (the process question, 2026-11-14). The approach choices below are this session's recommendations after the architecture critic's round (`.dforge/critic-2026-11-14-v1-w12e-security-residuals-design-report.md`), put to the owner at the spec review.

- **D1, residual A (row 176): remember the addresses nginx holds.** nginx resolves a custom location's static `proxy_pass` when it loads its configuration and keeps the answers while the name has none, or has moved: the premise of `forwardTargets` (`internal/modules/npm/network_claims.go:823-826`) that a name with no answer "can reach NPM only after it is re-pointed" is false, for a name with no answer and for one that now answers another address (the critic's variant: the alias gains a holder on a network NPM stays on). The agent keeps, in a new table `npm_forward_seen` (migration `0003`), the addresses each forward name answered when Darkpanel last wrote to NPM, and `forwardTargets` adds those addresses to the targets of the names NPM's proxy hosts and locations forward to now, beside the answers read now. Every Darkpanel write that makes NPM reload nginx (`npm.proxyhost.add`, `update`, `remove` and their undos) replaces the table before the write: for each name forwarded after the write, the answers read then, or the earlier record when the name has no answer then (nginx fails to resolve it and keeps its earlier workers); a name no proxy host forwards is dropped. An upgrade rebuilds it from the answers read after the recreate, with no earlier record kept, because nginx starts afresh. A host with no record reads as today (current answers only), until its first write. Rejected: refusing a join while a name has no answer (the critic's High: it leaves the re-answered variant open and blocks `panel.exposure.add`'s attach step while any proxy host names a stopped container); accepting A as part of the `forward host` residual (an alias is not a DNS name, and the accepted text at `docs/security/threat-model.md:338` says DNS); restarting NPM so nginx re-resolves (it interrupts every proxied site). A write through NPM's own admin UI is not recorded; it needs the NPM administrator. **Open (U1, Fable F2, High):** nginx also re-resolves at times no Darkpanel write marks: NPM's own reload every 6 hours (`ip_ranges.js`), `npm.certificate.request` (`certificate.go:265`), and every start of nginx (the upgrade's rollback and restore, `instance_upgrade.go:611,697`; recovery, `upgrade_recover.go:77,107`; the restart policy, `deps.go:461`), so the record as written does not hold what nginx holds (R3); the owner decides U1 at the spec review. If the record stays: a name's record is never reduced and a name never dropped unless the write's NPM call answered success and every recorded name answered at that write, otherwise the write adds the answers read now to the earlier record (R4, because NPM aborts the whole reload at the first failed `nginx -t`); `npm.instance.upgrade` and D2's undo count the answers read now only, since nginx starts afresh in the recreated container (R5).
- **D2, residual B (row 177): check the undo of a finished upgrade.** `Inverse` of `npm.instance.upgrade` in phase `done` runs a forward check before `rollback` and `restore`, on what `restore` recreates: the networks and static addresses of the upgrade row's `Config` (`instance_upgrade.go:181-207,683-689`) and `darkpanel-npm`, with the upgraded container's addresses counted as free. The reason of ruling W12a-R1, that a refusing rollback would leave NPM down, holds for the rollback of a failed upgrade and for recovery, which stay unchecked; it does not hold for a requested undo of a finished upgrade. `Inverse` in phase `done` runs `checkArchives`, then makes the original image available (the pull at `instance_upgrade.go:667`), then the forward check, then `rollback` (R7: a check before the pull leaves a window a caller can stretch by removing the unused original image). The check refuses, Definite and with nothing changed, when a network of `u.Config` no longer exists (R8: today that undo removes the upgraded container at `:671` and fails at `connect`, `:689`, leaving NPM down). When NPM's API does not answer, the undo is refused with `npm.unhealthy`, as the upgrade's own check is (`:115-119`, `network_claims.go:980-981`): a finished upgrade whose API stops answering cannot be undone until NPM answers again (R9).
- **D3, residual C (row 142): a late check in the upgrade, no lock.** The upgrade runs a second forward check after the pull (`instance_upgrade.go:220-222`) and before the effect is journaled (`:227`) and the container stopped (`:302`), and returns the Definite `npm.reserved` itself, so nothing is journaled and NPM is never stopped (R10). It cannot run after the stop: `forwardCheck` lists proxy hosts through NPM's API at `127.0.0.1:81` (`deps.go:50`), which the stopped container no longer serves, and a refusal inside `steps` loses its code in `fail` (`:253`, `:283-288`). The window in which an `operate` caller can free a forwarded address shrinks from the pull onward to the stop (grace 30 s, `:34`), both archives and the recreate; it is narrowed, not closed: a caller who polls the NPM container's state can still land `docker.container.stop` of the holder inside it (R12, Fable F4). **Open (U2, High):** the owner decides at the spec review whether row 142 closes by a check after the join or as an accepted risk. Rejected: adding the `docker` lock key to attach, detach and upgrade (the critic's High: `takeLocks` bumps the epoch of every key taken, so any Docker action would close the undo window of those actions, and a composite unwind such as `panel.exposure.add`'s would end in `needs_repair`; the Cloudflare and panel network actions free addresses under other keys anyway).
- **D4, row 6: the guard builds the IPv6 leg of a `[::]` binding on a link-local-only host.** Only `npmPublicFlows` (`internal/modules/firewall/guard/flows.go:408`, the exclusion at `:421`) stops excluding link-local addresses; `wildcardDsts` (`guard/route.go:248`) is not changed, because it already keeps the reply route's preferred address (`route.go:249`), a link-local one on such a host, and excludes only the other link-local addresses (`:256`). The flow is `standIn`, so a cell whose reply has no route is skipped. The link-local leg is probed at the one address the reply route prefers, on every interface, so a rule keyed on another interface's link-local destination address is not seen (R19). On a link-local-only host that has an IPv6 default route (from router advertisements) the `2000::/3` cells have a reply route, so the refusal of A9 reaches every client of the exposure, not only a hidden one (R16, Fable F8). Rejected: also dropping the exclusion in `wildcardDsts` (the critic's High: it changes every IPv6 wildcard flow on every host and probes the link-local addresses of `docker0` and every veth, which security rows 27 and 28 left out on purpose); an `unknown` flow, which would refuse every guarded change on every IPv4-only host.
- **D5, row 178: the Tailscale link guard protects the visible client of an NPM exposure.** For a request through an exposure whose client is not a host address, the guard adds the client's flow to each public binding, as `linkListenFor` does for a direct client. A client that is a host address (a tailnet client that Docker's userland proxy carries) is the hidden client; it gets no flow, and the threat model names that case as a residual, recorded as a new low register row. The added flow applies only to `Via.Kind == "npm"`, carries the request mark, and mirrors `linkguard.go:186-192` with `linkListenFor` (`:351-364`); the stale comment at `:179` is corrected. The new row says that every IPv6 tailnet client is hidden while NPM's networks are IPv4 only (`flows.go:307-310`), which is the usual path for a MagicDNS name, not a corner case (R17). Rejected for now: a stand-in tailnet flow per binding for the hidden client, which needs its own design in `linkguard.go`.
- **D6, row 179: cut the forward host at its first `/` in `checkRestoredLocation`** (`internal/modules/npm/proxyhost_edit.go:241`), before the empty and `$` tests at `:242`, as `forwardTargets` does (`network_claims.go:854-862`); a cut placed after them leaves `<NPM address>/$request_uri` unchecked (R18).
- **D7: the accepted DNS risk stays.** A caller who controls a DNS name that nginx's resolver answers differently from the agent's can still publish NPM's own API (Known residual risks, `forward host`); D1 to D3 close the paths that need no such name, including a Docker alias the caller controls. The threat model says so next to each fix.
- **D8: no harness change.** The fixes are guard and lifecycle logic covered by unit tests; D4's tests are built from route answers and addresses captured read-only from real hosts (`ip -6 addr`, `ip -6 route`, `ip -6 route get fe80::1`) rather than written by hand; gate 7 reruns on the merge.
- Early CI: none. The CI configuration has no platform this host does not cover (`ci.yml` on the self-hosted Linux runner, `harness.yml` on ubuntu-24.04), and D8 adds no harness step.

Finish: merge

## Riskiest assumption

On an IPv4-only host (IPv6 addresses link-local only, no IPv6 default route), the one-line change of D4 does not make the guard refuse its ordinary changes: the global-source cells of the `[::]` leg have no reply route and are skipped by `standIn`, and only link-local sources are evaluated. Evidence: `standIn` skips a wild source in a cell of a route without a path that no reply reaches (`internal/modules/firewall/guard/flows.go:65`, `route.go:121`); how the kernel answers a route lookup for a link-local source with no output interface is unverified — the plan's first task captures, read-only from a real IPv4-only Docker host (this host, if it is one), `ip -6 addr`, `ip -6 route` and the agent's own `netstat.RouteGet` answers for the lookups that decide the skip: a `2000::/3` address with no source (`route.go:119`), the same from each local link-local address and from `::1` (`noReplyFrom`, `route.go:227-241`), an `fe80::/64` address with no source, and the same from the address that answer prefers (`route.go:160-164`) (R14). D4 is built only if the global lookups answer ENETUNREACH, EHOSTUNREACH or EACCES (`netstat/routes.go:104`); any other errno makes the flow unknown and refuses every guarded change through the exposure. If wrong, D4 fails closed on every IPv4-only host, and A9's question widens to every guarded change.
