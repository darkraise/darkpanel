## Decisions

Quoted answers of the owner: "fix them all;" (every open row of the re-review, rows 190-199 and the raised row 188, including the ones the panel left for a ruling); "Full dforge flow (Recommended)" (the process question, 2026-11-15); "Check at agent start and on a timer (Recommended)" (row 191). The choices below are this session's recommendations after reading the code; the spec review puts the ones rated below `high` to the owner.

- **D1, row 190 (and rows 1, 176): the attach and the undo of a detach hold no window a caller can stretch.** The critic found that a lock cannot do this job: the cloudflare connector actions (`cloudflare.network.detach`, `cloudflare.connector.stop`, `cloudflare.connector.run`) free container addresses under the `cloudflare` lock only, and adding `docker` to the attach's keys would close the undo window of every composite that attaches NPM (`core/lifecycle/locks.go:21-55`, `undo.go:166-175`). So no key is added. The attach orders its work instead, as the upgrade's start check does (w12e D3): after the first reload it reads the forward targets once, literal addresses and the answers of every name, and then reads the network again and refuses, Definite and before it connects, when a target is now assignable to NPM on it; it connects; it inspects NPM at once and compares the addresses NPM took with those targets, with no API call and no lookup in between, and disconnects NPM on a hit; only then does it reload nginx and read the targets afresh for the second comparison, as before. The exposure that remains is the interval from the connect to the inspection, which Darkpanel's own calls fix and no caller can stretch, the class w12e D3 and the threat model (`threat-model.md:298`) already record for starts; the proxy-host listing and the name lookups, which a caller could slow, no longer sit inside it. The undo of a detach is built the same way.
- **D2, row 188 (also rows 196, 199): reload nginx by `docker exec`, not by re-sending a proxy host.** NPM's own reload is `nginx -t -g "error_log off;"` and then `nginx -s reload` (`docs/dforge/notes/w12e-evidence.md`, section 1, `/app/internal/nginx.js:108-121`). `reloadNginx` runs those two commands in `darkpanel-npm` through the Engine's exec API and reads only the exit codes. Nothing is written to NPM, so no proxy host file is renamed to `.err`, a concurrent edit in NPM's UI is never overwritten, no proxy host has to exist, NPM's API need not answer, and a missing `meta.nginx_online` cannot count as confirmed. This supersedes the update-based mechanism of w12e D1; w12e D1's other parts (a reload before and after the join, an unconfirmed reload refuses, the old workers' residual) stand. The Engine client has no exec call: `dockerapi` gains create, start (detached) and inspect of an exec, which the module reaches through its `dockerAPI` interface. The output of `nginx -t` is never read, so it cannot reach an error. A zero exit of `nginx -s reload` proves the signal was delivered, not that the master applied the configuration; the update path returned at the same point, and w12e D1 and `threat-model.md:299` record that as the owner's accepted residual, so D2 is no weaker (the critic's call for a worker-process check is not adopted: it needs `ps` or `/proc` inspection of an image that is not read here, to narrow a race the owner has accepted). The exec is a narrow adapter, not a general one: the container is fixed to `darkpanel-npm` and the two command lines are fixed, so the module cannot run another command through it. The bound of 10 seconds is for the pair of commands together. The Engine cannot kill an exec, so reloads are serialized inside the agent and a reload that finds an earlier exec of its own still running refuses with `npm.unhealthy` without starting a second. The exec runs as the user NPM's own backend runs `nginx -t` as (the `PUID` and `PGID` of the container's environment, root when they are not set), so it leaves no file under nginx's log or temp directories owned by another user. When `nginx -t` fails, the refusal names the cause the way D4 does: the unanswered static forwards, with their location and host, under `npm.forward_unanswered`.
- **D3, row 191 (owner's answer: agent start and a timer): a background task `npm.reconcile`.** It runs a first pass at the agent's start, every 5 minutes (`firewall.reconcile` is the model, `internal/modules/firewall/reconcile.go:17-34`), and on each `start` event of the container `darkpanel-npm` and each `connect` event of it to a network. A pass is read-only until it finds a hit: it inspects `darkpanel-npm`, compares the addresses it holds on every network with the forward targets (literal addresses first, then names), and only on a hit calls `tc.Apply` of a new admin action `npm.instance.reconcile`, class irreversible, lock keys `["npm"]`. The action's input is empty. Its Plan and Apply find the hits again under the lock, since an attach, a detach or an upgrade can finish between the pass's read and the apply, and an apply that finds none changes nothing; its state hash covers NPM's endpoints and the targets. It disconnects NPM from each network where it holds a forwarded address (as `verifyHeld`'s `dropNetwork` does) and reloads nginx. When the reload then fails, NPM stays disconnected and the change fails with `npm.unhealthy`, naming the networks it dropped. The change's result lists each network dropped and the claimants that held a claim on it, and a log line says the same; the claims stay, and the operator attaches again, which the guard now checks. A hit on `darkpanel-npm` itself leaves NPM running and fails with `npm.reserved`; a pass reports the same hit once and does not apply again until the hit changes, so the ledger does not fill. A pass skips while no instance is deployed, NPM is not running, or the `npm` lock is held. It also backstops D5: an NPM administrator who enables a disabled proxy host that forwards to an address NPM holds has it live until the next pass, at most 5 minutes (no event sees it); the threat model records that window. Every pass logs in to NPM once to list the proxy hosts, about 288 logins a day, which is acceptable. The window between an Engine or host restart and the pass is the event's latency, or 5 minutes without it.
- **D4, row 192: the upgrade refuses up front when nginx could not start the recreated container.** A custom location's forward host is a static `proxy_pass` name that nginx resolves when it loads its configuration, and a name with no answer fails the load (`w12e-evidence.md` section 3 and 5; the second is inference). The upgrade's two forward checks (before and after the pull, `instance_upgrade.go:200,243`) refuse, Definite and with NPM left running, when an enabled proxy host has a custom location whose forward host is a name (not an address, not holding `$`) that has no answer. The unanswered static forwards come from a separate function that only the upgrade checks and D2's refusal detail call, so `forwardTargets` and the join guard see no address-less target. The refusal carries a new code `npm.forward_unanswered` (409, title "Forward host has no answer") whose detail names the location and the host. The spec's promise of this refusal (w12e design, self-review) was dropped without a ruling; this restores it. The default location's name is resolved per request, so it does not block nginx's start and is not checked.
- **D5, rows 193, 194: the join guard looks only at enabled hosts, and its refusals keep their detail.** A disabled proxy host has no nginx configuration (`w12e-evidence.md` section 1: "No need to add nginx config if host is disabled"), and Darkpanel's `npm.proxyhost.update` does not carry `enabled`, so only an NPM administrator can enable one, and D3 is the backstop for that; `forwardTargets` skips hosts with `Enabled` false. The two refusals of a forward name that could not be resolved (`network_claims.go:1007,1068`) change from `unavailable` (503, whose detail a 5xx answer drops, `agent/api/handler.go:871`) to a new code `npm.forward_unresolved` (409, title "Forward host could not be resolved"), kept apart from `npm.reserved` so that automation can tell a conflict from a failure to retry, so the failing forward host and "retry" reach the client. An enabled host whose name gets no definite answer still refuses every join: the guard cannot show the name is not one of NPM's addresses, and failing closed on that was the decision of row 143. The filter by the requested network that Codex floated is not adopted: nginx resolves a name through every network NPM is on, so a name unrelated to the new network can still change.
- **D6, row 195: the harness no longer calls NPM's API.** The step `reload-follows-name` re-implemented the reload with a bearer token in `curl` command text (`test/harness/m6_npm_test.go:1073`, and the harness copies the whole command into failures, `test/harness/vm/vm.go:319,342`). D2 removes the reload call, so `reloadCall` and its token are deleted. The failure half drives the real `npm.network.attach` instead: a proxy host with a custom location forwarding to a dotted name that gets a definite not-found (inference: a dotted `.invalid` name does, where a single label did not, `w12e-evidence.md` and the w12f harness run), the attach is refused `npm.reserved` before NPM joins, and the moved-name half asserts what it did before.
- **D7, row 198: four small defects of the join.** (a) An attach on a network NPM is already on (an earlier apply cut off after the connect) runs the held-address check and one reload, as the undo of a detach does (w12e R25); a hit disconnects NPM and refuses, the same outcome D3 reaches at its next pass, so a claimant on that network loses NPM and the refusal's detail says so. (b) A joined NPM with no endpoint on the network is a failed check: `joinedProblem` disconnects and refuses instead of treating it as holding nothing (`network_claims.go:875`). (c) `reloadBeforeJoin` refuses with `npm.reserved` only when nginx's test failed; an exec failure, a timeout or a missing container refuses with `npm.unhealthy`. (d) `verifyStart` returns `held.Unverified` as the existing `unverifiedStart` report rather than logging it (`instance_upgrade.go:762-766`), as w12e R29 says.
- **D8, row 199 and the threat model.** The Tailscale link guard adds an unknown flow for an NPM exposure with no public binding, as the firewall guard does (`internal/modules/firewall/guard/flows.go:285`), so a change that cannot be shown safe is refused. `docs/security/threat-model.md` is corrected where the code differs: the reload paragraph (D2), the residual-risk lines on the reload, the 5xx detail, the starts Darkpanel does not make (D3), the literal-address sentence ("no caller can stretch it" holds for starts only; for the attach D1 now holds it to the connect-to-inspection interval), and the sentence that says the proxy-host update against a running NPM was not run.
- **D9, row 197: test hygiene.** `qaSpan` in `internal/modules/firewall/guard/w12e_security_residuals_acceptance_test.go:21` is replaced by `w12eNamesIPv6Range`; the stale comment at `internal/modules/npm/network_claims_test.go:1159` and `TestW12eAttachDeadlines` (`w12e_attach_test.go:300`), which compares constants and omits the two lookup passes, are corrected.
- **D10: what stays accepted.** The old workers' residual (w12e D1 (a)), the DNS re-pointing risk (w12e D7), and the window between a connect and the inspection that follows (w12e D3) stay as they are; D1 narrows the last for an attach from "up to the lookups" to the connect-to-inspection interval itself. The harness reruns on the merge (gate 7), and D2, D3, D4 and D6 each get a live step or a live check (A7, A11).
- Early CI: none. The CI configuration has no platform this host does not cover (`ci.yml` on the self-hosted Linux runner, `harness.yml` on ubuntu-24.04).

Finish: merge

## Acceptance

A2. [test, neg, high] When NPM took an address that a proxy host forwards to by literal or through a name read before the connect, the attach disconnects NPM again right after its inspection, before it reloads nginx or reads the targets afresh; the undo of a detach does the same.

## Riskiest assumption

That `nginx -t -g "error_log off;"` followed by `nginx -s reload` can be run by an exec in `darkpanel-npm` of the pinned image, as the user the exec starts with, and that its exit codes tell a failed test from a reload signal. Evidence: NPM runs these same two commands from its own code (`w12e-evidence.md` section 1, `/app/internal/nginx.js:108-121`); the image starts nginx as `PUID:PGID` under s6 (`w12e-evidence.md` section 5), so whether the exec's user (D2: the container's `PUID` and `PGID`) can run `nginx -t` and signal nginx without leaving files another user owns is unverified — the plan's first task verifies it, on the pinned image in the harness, before the rest is built on it. If it cannot, the exec runs as the user the nginx process runs as, which the Engine's exec call can set.

## Critic findings

Critic: 1 Blocker, 2 High (3 fixed, 0 answered), 9 Medium, 3 Nit (report `.dforge/critic-2026-11-15-v1-w12g-security-followup-design-report.md`).

- Blocker, D1's premise that every address-freeing action takes the `docker` lock is false (the cloudflare connector actions): fixed by dropping the lock; D1 orders the attach's work instead, and A19 names both modules.
- High, a `docker` key would close the undo window of every composite that attaches NPM: fixed by the same change; A20 adds an unwind test.
- High, a zero exit of `nginx -s reload` is not a confirmed application: the design stands; it is the owner's accepted residual of w12e D1 (`threat-model.md:299`), the update path was no stronger, and a worker-process check needs image inspection that is not read here. D2 says so.
- Medium, the exec surface: D2 makes it a narrow adapter with the container and the commands fixed, a 10-second bound on the pair, serialized reloads and a refusal while an earlier exec runs; the plan recomputes the attach budgets, which D1 shortens by removing lookups from the held interval.
- Medium, the exec's user: D2 and the riskiest assumption use the container's `PUID` and `PGID`; A7 checks file ownership in the harness.
- Medium, nothing names the broken static name after D2: D2 and A4 use `npm.forward_unanswered`.
- Medium, unanswered forwards inside `forwardTargets`: D4 puts them in a separate function; A12 checks the guard's targets stay the same.
- Medium, a hit on `darkpanel-npm` fails every pass: D3 reports it once; A10.
- Medium, the dropped exposure is never restored or reported: D3 records the networks and claimants and leaves the claims; the operator attaches again. No automatic re-attach, which could loop.
- Medium, `npm.instance.reconcile` deciding again under its locks: D3 gives it an empty input, a recomputed plan and the failed-reload outcome; A9.
- Medium, `npm.reserved` for an unresolved name: D5 adds `npm.forward_unresolved`; A14.
- Medium, disabled hosts and the administrator's enabling: D3 is named the backstop and the 5-minute window goes in the threat model; A13 has the case.
- Nit, connect events: D3 and its file list. Nit, A15's question: D7 states the outcome matches D3. Nit, a login per pass: D3 accepts about 288 a day.
