## Decisions

Quoted answers of the owner: "fix them all;" (every open row of the re-review, rows 190-199 and the raised row 188, including the ones the panel left for a ruling); "Full dforge flow (Recommended)" (the process question, 2026-11-15); "Check at agent start and on a timer (Recommended)" (row 191). The choices below are this session's recommendations after reading the code; the spec review puts the ones rated below `high` to the owner.

- **D1, row 190 (and rows 1, 176): `npm.network.attach` and `npm.network.detach` also take the `docker` lock.** Every Darkpanel action that can free an address (`docker.network.disconnect`, `docker.container.stop`, remove, compose) takes the `docker` lock (`internal/modules/docker/deps.go:16`), the attach takes only `npm` (`internal/modules/npm/deps.go:34`), and `LockKeys` is a list (`core/contract.go:220`), so declaring `["npm", "docker"]` makes the lifecycle engine refuse a docker change while an attach holds the keys (`core/lifecycle/apply.go:182`, `locksFree`). That removes the interleaving for every `operate` caller, whatever the lookups take. The undo of a detach runs under the detach's keys (`core/registry.go:472`), so the detach declares both too. Two further changes keep the window small against an actor outside Darkpanel (the host's own `docker` CLI), and make the check cheaper than the lookups it used to wait for: `joinedProblem` compares the literal forward targets with the addresses NPM took before it resolves any name, as `verifyHeld` does (`instance_upgrade.go:466`); and the attach reads the network again after the first reload and refuses, Definite and before it connects, when a literal target is now assignable to NPM.
- **D2, row 188 (also rows 196, 199): reload nginx by `docker exec`, not by re-sending a proxy host.** NPM's own reload is `nginx -t -g "error_log off;"` and then `nginx -s reload` (`docs/dforge/notes/w12e-evidence.md`, section 1, `/app/internal/nginx.js:108-121`). `reloadNginx` runs those two commands in `darkpanel-npm` through the Engine's exec API and reads only the exit codes. Nothing is written to NPM, so no proxy host file is renamed to `.err`, a concurrent edit in NPM's UI is never overwritten, no proxy host has to exist, NPM's API need not answer, and a missing `meta.nginx_online` cannot count as confirmed. This supersedes the update-based mechanism of w12e D1; w12e D1's other parts (a reload before and after the join, an unconfirmed reload refuses, the old workers' residual) stand. The Engine client has no exec call: `dockerapi` gains create, start (detached) and inspect of an exec, which the module reaches through its `dockerAPI` interface. The output of `nginx -t` is never read, so it cannot reach an error.
- **D3, row 191 (owner's answer: agent start and a timer): a background task `npm.reconcile`.** It runs a first pass at the agent's start, every 5 minutes (`firewall.reconcile` is the model, `internal/modules/firewall/reconcile.go:17-34`), and on each `start` event of the container `darkpanel-npm`. A pass is read-only until it finds a hit: it inspects `darkpanel-npm`, compares the addresses it holds on every network with the forward targets (literal addresses first, then names), and only on a hit calls `tc.Apply` of a new admin action `npm.instance.reconcile`, class irreversible, lock keys `["npm", "docker"]`. That action disconnects NPM from each network where it holds a forwarded address (as `verifyHeld`'s `dropNetwork` does), reloads nginx, and on a hit on `darkpanel-npm` itself leaves NPM running and fails with `npm.reserved`, since stopping it would leave NPM down. A pass with no hit records no change. A pass skips while no instance is deployed, NPM is not running, or the keys are held. A claim on a network NPM is dropped from stays; its claimant's verify then fails visibly. The window between an Engine or host restart and the next pass is at most the event's latency, or 5 minutes without it.
- **D4, row 192: the upgrade refuses up front when nginx could not start the recreated container.** A custom location's forward host is a static `proxy_pass` name that nginx resolves when it loads its configuration, and a name with no answer fails the load (`w12e-evidence.md` section 3 and 5; the second is inference). The upgrade's two forward checks (before and after the pull, `instance_upgrade.go:200,243`) refuse, Definite and with NPM left running, when an enabled proxy host has a custom location whose forward host is a name (not an address, not holding `$`) that has no answer. `forwardTargets` also returns those unanswered static forwards. The refusal carries a new code `npm.forward_unanswered` (409, title "Forward host has no answer") whose detail names the location and the host. The spec's promise of this refusal (w12e design, self-review) was dropped without a ruling; this restores it. The default location's name is resolved per request, so it does not block nginx's start and is not checked.
- **D5, rows 193, 194: the join guard looks only at enabled hosts, and its refusals keep their detail.** A disabled proxy host has no nginx configuration (`w12e-evidence.md` section 1: "No need to add nginx config if host is disabled"), and Darkpanel's `npm.proxyhost.update` does not carry `enabled`, so only an NPM administrator can enable one; `forwardTargets` skips hosts with `Enabled` false. The two refusals of a forward name that could not be resolved (`network_claims.go:1007,1068`) change from `unavailable` (503, whose detail a 5xx answer drops, `agent/api/handler.go:871`) to `npm.reserved` (409), so the failing forward host and "retry" reach the client. An enabled host whose name gets no definite answer still refuses every join: the guard cannot show the name is not one of NPM's addresses, and failing closed on that was the decision of row 143. The filter by the requested network that Codex floated is not adopted: nginx resolves a name through every network NPM is on, so a name unrelated to the new network can still change.
- **D6, row 195: the harness no longer calls NPM's API.** The step `reload-follows-name` re-implemented the reload with a bearer token in `curl` command text (`test/harness/m6_npm_test.go:1073`, and the harness copies the whole command into failures, `test/harness/vm/vm.go:319,342`). D2 removes the reload call, so `reloadCall` and its token are deleted. The failure half drives the real `npm.network.attach` instead: a proxy host with a custom location forwarding to a dotted name that gets a definite not-found (inference: a dotted `.invalid` name does, where a single label did not, `w12e-evidence.md` and the w12f harness run), the attach is refused `npm.reserved` before NPM joins, and the moved-name half asserts what it did before.
- **D7, row 198: four small defects of the join.** (a) An attach on a network NPM is already on (an earlier apply cut off after the connect) runs the held-address check and one reload, as the undo of a detach does (w12e R25); a hit disconnects NPM and refuses. (b) A joined NPM with no endpoint on the network is a failed check: `joinedProblem` disconnects and refuses instead of treating it as holding nothing (`network_claims.go:875`). (c) `reloadBeforeJoin` refuses with `npm.reserved` only when nginx's test failed; an exec failure, a timeout or a missing container refuses with `npm.unhealthy`. (d) `verifyStart` returns `held.Unverified` as the existing `unverifiedStart` report rather than logging it (`instance_upgrade.go:762-766`), as w12e R29 says.
- **D8, row 199 and the threat model.** The Tailscale link guard adds an unknown flow for an NPM exposure with no public binding, as the firewall guard does (`internal/modules/firewall/guard/flows.go:285`), so a change that cannot be shown safe is refused. `docs/security/threat-model.md` is corrected where the code differs: the reload paragraph (D2), the residual-risk lines on the reload, the 5xx detail, the starts Darkpanel does not make (D3), the literal-address sentence ("no caller can stretch it" holds for starts only, and the attach is now under the docker lock), and the sentence that says the proxy-host update against a running NPM was not run.
- **D9, row 197: test hygiene.** `qaSpan` in `internal/modules/firewall/guard/w12e_security_residuals_acceptance_test.go:21` is replaced by `w12eNamesIPv6Range`; the stale comment at `internal/modules/npm/network_claims_test.go:1159` and `TestW12eAttachDeadlines` (`w12e_attach_test.go:300`), which compares constants and omits the two lookup passes, are corrected.
- **D10: what stays accepted.** The old workers' residual (w12e D1 (a)), the DNS re-pointing risk (w12e D7), and the window between a connect and the inspection that follows (w12e D3) stay as they are; D1 narrows the last for an attach from "up to the lookups" to the inspection itself. The harness reruns on the merge (gate 7), and D2, D3, D4 and D6 each get a live step or a live check (A7, A11).
- Early CI: none. The CI configuration has no platform this host does not cover (`ci.yml` on the self-hosted Linux runner, `harness.yml` on ubuntu-24.04).

Finish: merge

A3. [test, high] After the first reload and before it connects, the attach reads the network again and refuses with `npm.reserved`, with NPM not connected, when a literal forward target is assignable to NPM on it; the undo of a detach does the same.
A4. [test, high] `reloadNginx` runs `nginx -t -g "error_log off;"` and then `nginx -s reload` in `darkpanel-npm` by exec, and a non-zero exit of the first refuses the join with `npm.reserved` before NPM connects.

## Riskiest assumption

That `nginx -t -g "error_log off;"` followed by `nginx -s reload` can be run by an exec in `darkpanel-npm` of the pinned image, as the user the exec starts with, and that its exit codes tell a failed test from a reload signal. Evidence: NPM runs these same two commands from its own code (`w12e-evidence.md` section 1, `/app/internal/nginx.js:108-121`); the image starts nginx as `PUID:PGID` under s6 (`w12e-evidence.md` section 5), so whether the exec's default user can signal it is unverified — the plan's first task verifies it, on the pinned image in the harness, before the rest is built on it. If it cannot, the exec runs as the user the nginx process runs as, which the Engine's exec call can set.
