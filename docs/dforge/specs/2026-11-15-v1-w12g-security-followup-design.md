## Decisions

Quoted answers of the owner: "fix them all;" (every open row of the re-review, rows 190-199 and the raised row 188, including the ones the panel left for a ruling); "Full dforge flow (Recommended)" (the process question, 2026-11-15); "Check at agent start and on a timer (Recommended)" (row 191; the question was "how should it be fixed?" for an NPM restarted by the Engine, the host or its restart policy that takes a forwarded address nobody verifies, and the option read: "The agent runs verifyHeld when it starts and every few minutes while NPM is running, and disconnects NPM from a network where it holds a forward target. Covers Engine restarts the agent does not see; adds one small background check."). The choices below are this session's recommendations after reading the code; the spec review puts the ones rated below `high` to the owner.

- **D1, row 190 (and rows 1, 176): the attach and the undo of a detach hold no window a caller can stretch.** The critic found that a lock cannot do this job: the cloudflare connector actions (`cloudflare.network.detach`, `cloudflare.connector.stop`, `cloudflare.connector.run`) free container addresses under the `cloudflare` lock only, and adding `docker` to the attach's keys would close the undo window of every composite that attaches NPM (`core/lifecycle/locks.go:21-55`, `undo.go:166-175`). So no key is added. The attach orders its work instead, as the upgrade's start check does (w12e D3). `Apply` and the undo of a detach run the forward guard once, on the targets they read after the first reload (literal addresses and the answers of every name; `Plan` keeps its own guard, which the engine runs again just before `Apply`, `lifecycle/apply.go:193`). They then read the network again and refuse, Definite and before connecting, when a target is now assignable to NPM on it; connect; inspect NPM at once and compare the addresses NPM took with those targets, with no API call and no lookup in between; and disconnect NPM on a hit. Only then do they reload nginx and read the targets afresh for the second comparison, as before. After a connect error that is not a refusal (a lost answer), they inspect NPM under `context.WithoutCancel` and, when NPM is on the network, run the held-address check and the disconnect as after a successful connect. The exposure that remains runs from the connect until the disconnect that follows the inspection has finished, bounded by `nginxDisconnectWait` (10 seconds); a caller who frees a forwarded address between the network re-read and the connect can repeat it by retrying. Darkpanel's own calls fix it and no caller can stretch it, as for starts (w12e D3, `threat-model.md:298`); the proxy-host listing and the name lookups, which a caller could slow, no longer sit inside it. The owner is asked to accept that interval in writing (spec review, U2). The undo of a detach is built the same way.
- **D2, row 188 (also rows 196, 199): reload nginx by `docker exec`, not by re-sending a proxy host.** NPM's own reload is `nginx -t -g "error_log off;"` and then `nginx -s reload` (`docs/dforge/notes/w12e-evidence.md`, section 1, `/app/internal/nginx.js:108-121`). `reloadNginx` runs those two commands in `darkpanel-npm` through the Engine's exec API (create, start detached with no stream attached, then poll inspect) and reads only the exit codes. Nothing is written to NPM, so no proxy host file is renamed to `.err`, a concurrent edit in NPM's UI is never overwritten, no proxy host has to exist, NPM's API need not answer, and a missing `meta.nginx_online` cannot count as confirmed. This supersedes the update-based mechanism of w12e D1; w12e D1's other parts (a reload before and after the join, an unconfirmed reload refuses, the old workers' residual) stand. The Engine client has no exec call, so `dockerapi` gains create, start and inspect of an exec. They stay out of the module's `dockerAPI` interface: `deps` gains one function, built in `productionNM`, that takes neither a container nor a command and runs the two fixed command lines in `darkpanel-npm`, so the module cannot run another command through it. The output of `nginx -t` is never read, so it cannot reach an error. An inspect answer with no exit code, or one still marked running at the bound, is unconfirmed and refuses with `npm.unhealthy`; so does a non-zero exit of `nginx -s reload`; only a non-zero exit of `nginx -t` refuses with `npm.reserved`, or with `npm.forward_unanswered` when an enabled custom location forwards to a name with no answer, naming the location and the host. After a failed second reload NPM is disconnected first and that detail, which needs a listing and lookups, is computed afterwards. The bound of 10 seconds is for the pair of commands together. The Engine cannot kill an exec; the `npm` lock already serializes the callers, and a reload that finds an exec of its own from a timed-out reload still running refuses with `npm.unhealthy` without starting a second (that memory does not survive an agent restart). The exec runs as the user of the container's `PUID` and `PGID` (root when they are not set, since Darkpanel creates the container with no environment, `deps.go:446-468`), which must be numeric or the reload refuses with `npm.unhealthy`. **The unapplied reload:** a zero exit of `nginx -s reload` proves the signal was delivered, not that the master applied the configuration. w12e D1 records the owner's acceptance only for the old workers' residual, not for this one, and a caller can force the race (a Docker action between the test and the reload). So the reload is confirmed: before the signal the module lists NPM's processes through the Engine (`GET /containers/{id}/top`, which runs nothing in the image), and after it polls until a worker of the nginx master appears that was not there before, refusing as unconfirmed otherwise; the plan's first task proves it on the pinned image on the four harness systems (spec review, U1; if the owner instead accepts the residual in writing, this sentence becomes a threat-model sentence marked as the owner's).
- **D3, row 191 (owner's answer: agent start and a timer): a background task `npm.reconcile`.** It runs a first pass at the agent's start, every 5 minutes (`firewall.reconcile` is the model, `internal/modules/firewall/reconcile.go:17-34`, and the runner at `internal/agent/runtime/background.go:159-208`), and on each `start` event of the container `darkpanel-npm` and each `connect` event of it to a network. A pass is read-only until it finds a hit: it inspects `darkpanel-npm`, compares the addresses it holds on every network with the forward targets (literal addresses first, then names; when the lookups fail the literal comparison has been made and the rest is logged), and only on a hit calls `tc.Apply` of a new action `npm.instance.reconcile`. A background task cannot apply an irreversible action (`lifecycle/system.go:28-30`), so the action is compensable with `ForwardOnly` and `Converges`, `MinScope` admin and `ApplyTimeout` 45 seconds, declared as `panel.listener.revoke` is (`panel/listener_revoke.go:19-25`); its lock keys are `["npm"]` and `docker` is not taken. Its input is empty and it has an output type. `Plan` runs before the lock is taken, so `Apply` finds the hits again under the lock, since an attach, a detach or an upgrade can finish in between, and an apply that finds none changes nothing; the state hash covers the hits (network, the address NPM holds there, NPM's endpoint id), not every target, so a name with rotating answers cannot fail every apply with `plan.state_changed`. The action disconnects NPM from each network where it holds a forwarded address (as `verifyHeld`'s `dropNetwork` does; a hit whose disconnect fails stops NPM, as w12e ruling R30 decided for `verifyHeld`) and reloads nginx. A failed reload leaves the change `failed`, lock released, NPM disconnected and the detail naming the networks, code `npm.unhealthy` (the detail adds the unanswered forwards as D2 does); a disconnect whose outcome is unknown leaves `needs_repair`. Its `Verify` inspects NPM and requires that it holds no forwarded address on any network. The change's result lists each network dropped and the claimants that held a claim on it, and a log line says the same; the claims stay, and the operator attaches again, which the guard now checks. A hit on `darkpanel-npm` itself leaves NPM running and fails with `npm.reserved`; a pass reports the same hit once, remembered in memory (so it repeats after an agent restart), and does not apply again until the hit changes. A pass skips while no instance is deployed, NPM is not running, or the `npm` lock is held. It backstops D5: an NPM administrator who enables a disabled proxy host that forwards to an address NPM holds has it live until the next pass. The limits, which the threat model states: after a `start` event NPM's API does not answer for up to 120 seconds (`instance_deploy.go:33`), so the first listing that works comes up to one backoff step after it first answers (`background.go:180-193`); a pass skipped for a held lock waits the full 5 minutes, and a change left in `needs_repair` keeps the `npm` lock without limit (`lifecycle/settle.go:93-101`), during which no pass runs; a name re-pointed to one of NPM's addresses takes NPM off that network within a pass, which is the accepted DNS risk now acting unattended; every reconcile change, the one that changes nothing included, raises the `npm` epoch and so closes the undo window of the last npm change (`lifecycle/locks.go:43-52`). Every pass logs in to NPM once to list the proxy hosts, about 288 logins a day, which is acceptable. The owner's answer names the unattended disconnect but not the stop on a failed disconnect, the networks joined by hand, or these limits; the spec review puts them (U3).
- **D4, row 192: the upgrade refuses up front when nginx could not start the recreated container.** A custom location's forward host is a static `proxy_pass` name that nginx resolves when it loads its configuration, and a name with no answer fails the load (`w12e-evidence.md` sections 3 and 5; that nginx does not start is inference, though the w12f harness saw `nginx -t` report the unanswered name, `w12e-evidence.md:326`). The upgrade's checks (the plan at `instance_upgrade.go:174`, and the two in `Apply` at `:237` and `:243`, before and after the pull) and `undoForwardCheck` (`upgrade_recover.go:60-88`, which does not call `forwardCheck`, and recreates the container the same way) refuse, Definite and with NPM left running, when an enabled proxy host has a custom location whose forward host is a name (not an address, not holding `$`) that has no answer. The unanswered static forwards come from a separate function that only the upgrade checks and D2's refusal detail call, so `forwardTargets` and the join guard see no address-less target. A refusal inside `Apply` leaves a failed change with no effect journaled and NPM never stopped, as in w12e A6. The refusal carries a new code `npm.forward_unanswered` (409, title "Forward host has no answer") whose detail names the location and the host. The spec's promise of this refusal (w12e design, self-review) was dropped without a ruling; this restores it. The default location's name is resolved per request, so it does not block nginx's start and is not checked.
- **D5, rows 193, 194: the join guard looks only at enabled hosts, and its refusals keep their detail.** A disabled proxy host has no nginx configuration (`w12e-evidence.md` section 1: "No need to add nginx config if host is disabled"), and Darkpanel's `npm.proxyhost.update` does not carry `enabled`, so only an NPM administrator can enable one, and D3 is the backstop for that; `forwardTargets` skips hosts with `Enabled` false. The two refusals of a forward name that could not be resolved (`network_claims.go:1007,1068`) change from `unavailable` (503, whose detail a 5xx answer drops, `agent/api/handler.go:871`) to a new code `npm.forward_unresolved` (409, title "Forward host could not be resolved"), kept apart from `npm.reserved` so that automation can tell a conflict from a failure to retry, so the failing proxy host or location and its forward host reach the client, with the cause that a stopped or removed container's name is the usual one on a resolver that gives no definite not-found, not only "retry"; the refusal at `network_claims.go:1007`, for the Docker names that could not be read in time, has no host to name and says to retry. An enabled host whose name gets no definite answer still refuses every join: the guard cannot show the name is not one of NPM's addresses, and failing closed on that was the decision of row 143. The filter by the requested network that Codex floated is not adopted: nginx resolves a name through every network NPM is on, so a name unrelated to the new network can still change.
- **D6, row 195: the harness no longer calls NPM's API.** The step `reload-follows-name` re-implemented the reload with a bearer token in `curl` command text (`test/harness/m6_npm_test.go:1073`, and the harness copies the whole command into failures, `test/harness/vm/vm.go:319,342`). D2 removes the reload call, so `reloadCall` and its token are deleted. The failure half drives the real `npm.network.attach` instead: a proxy host with a custom location forwarding to a dotted name that gets a definite not-found (inference: a dotted `.invalid` name does, where a single label did not, `w12e-evidence.md` and the w12f harness run), the attach is refused `npm.forward_unanswered` before NPM joins, and the moved-name half asserts what it did before.
- **D7, row 198: four small defects of the join.** (a) An attach on a network NPM is already on and that has no claim, the one state an apply cut off after the connect leaves, runs the held-address check and one reload; a hit or an unconfirmed reload disconnects NPM and refuses as after a fresh join, the same outcome D3 reaches at its next pass, except on `darkpanel-npm`, which NPM never leaves (a hit fails with `npm.reserved`). An attach on a network that already has a claim stays a claim-only change, so no `operate` caller can get NPM disconnected from a shared network by making `nginx -t` fail. (b) A joined NPM with no endpoint on the network is a failed check: `joinedProblem` disconnects and refuses instead of treating it as holding nothing (`network_claims.go:875`). (c) `reloadBeforeJoin` refuses with `npm.reserved` (or `npm.forward_unanswered`) only when nginx's test failed; an exec failure, a timeout, an absent exit code, a failed reload and a missing container refuse with `npm.unhealthy`. (d) `verifyStart` writes `held.Unverified` to the upgrade row's result and names it in the change's error where the change fails anyway, and the rollback, undo or recovery completes (as w12e R29 says); it is not turned into a failed rollback, whose retry restores from the archives again (`instance_upgrade.go:703-727`). `npm.reconcile` verifies the running container at its next pass.
- **D8, row 199 and the threat model.** The Tailscale link guard adds an unknown flow for an NPM exposure with no public binding, as the firewall guard does (`internal/modules/firewall/guard/flows.go:285`), so a change that cannot be shown safe is refused. `docs/security/threat-model.md` is corrected where the code differs: the reload paragraph (D2), the residual-risk lines on the reload, the 5xx detail, the starts Darkpanel does not make (D3), the literal-address sentence ("no caller can stretch it" holds for starts only; for the attach D1 now holds it to the connect-to-inspection interval), and the sentence that says the proxy-host update against a running NPM was not run.
- **D9, row 197: test hygiene.** `qaSpan` in `internal/modules/firewall/guard/w12e_security_residuals_acceptance_test.go:21` is replaced by `w12eNamesIPv6Range`; the stale comment at `internal/modules/npm/network_claims_test.go:1159` and `TestW12eAttachDeadlines` (`w12e_attach_test.go:300`), which compares constants and omits the two lookup passes, are corrected.
- **D10: what stays accepted, and what does not.** Recorded as the owner's: the old workers' residual (w12e D1 (a), U4 (a), `threat-model.md:299`) and the DNS re-pointing risk (w12e D7, which the 2026-11-12 re-review also records; `threat-model.md:343` words it as inherent). Not recorded as the owner's, so put to the owner at the spec review: the unapplied reload (U1, D2), the connect-to-disconnect interval of an attach (U2, D1) and what D3 does unattended (U3). The harness reruns on the merge (gate 7), and D2, D3, D4 and D6 each get a live step or a live check (A7, A11).
- Early CI: none. The CI configuration has no platform this host does not cover (`ci.yml` on the self-hosted Linux runner, `harness.yml` on ubuntu-24.04).

## Riskiest assumption

That `nginx -t -g "error_log off;"` followed by `nginx -s reload` can be run by an exec in `darkpanel-npm` of the pinned image, as the user the exec starts with, and that its exit codes tell a failed test from a reload signal. Evidence: NPM runs these same two commands from its own code (`w12e-evidence.md` section 1, `/app/internal/nginx.js:108-121`); the image starts nginx as `PUID:PGID` under s6 (`w12e-evidence.md` section 5), so whether the exec's user (D2: the container's `PUID` and `PGID`) can run `nginx -t` and signal nginx without leaving files another user owns is unverified — the plan's first task verifies it, together with the Engine's process listing (`GET /containers/{id}/top`) that D2's confirmation of the reload reads, on the pinned image in the harness, before the rest is built on it. If it cannot, the exec runs as the user the nginx process runs as, which the Engine's exec call can set.
