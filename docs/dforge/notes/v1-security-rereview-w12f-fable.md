## Other observations
- **The reload can take an unrelated proxy host offline (the "Also check" item).** `reloadNginx` re-sends the enabled proxy host with the lowest id (`internal/modules/npm/nginx_reload.go:30-39`). NPM tests nginx, regenerates that host's file and tests again; a second test that fails is blamed on that host, whose file is renamed to `.err` (evidence note, NPM image section 1). `nginx -t` tests every file, so the second test fails when any static name anywhere stops answering between the two tests. An `operate` caller reaches this: they forward their own proxy host to a Docker alias they control, start an attach (or the undo of a detach), and disconnect the alias's container between NPM's two tests; the host that goes offline is the lowest-id enabled one, which can be a host the caller may not change, such as the panel exposure's reserved host. It stays offline until its next successful update or the next join's reload. Related: when the lowest-id enabled host is already offline in NPM, every join is refused although nginx serves every other host. plausible (NPM's and nginx's behaviour is inference; the selection and the caller's actions are read in code); medium, availability; `threat-model.md:301` records the mechanism as "a change between the two tests" but not that a caller can cause it or that the host can be a reserved one; not marked owner-accepted.
- **One unanswered forward name blocks every new NPM join (the "Also check" item).** `forwardAnswers` skips only a definite not-found; any other lookup outcome refuses with `unavailable` (`internal/modules/npm/network_claims.go:1060-1071`), and a name that no container on NPM's networks answers goes to the host's resolver (`:1012-1018`), including the name of a container that was stopped or disconnected. On a host whose resolver gives no definite not-found for a single-label name, one such proxy host or kept custom location refuses every attach that has to connect (plan and apply, `:320`), every undo of a detach (`:800`), every upgrade (`instance_upgrade.go:174`, `:237`) and the undo of a finished upgrade (`upgrade_recover.go:74`). At plan the client sees only the title "Unavailable": a 5xx problem drops its detail (`internal/controller/api/wire.go:48-49`; the same pattern matches at `internal/agent/api/handler.go:871-877`, found by search), so the forward host named at `network_claims.go:1068-1069` reaches only the log. Where the resolver does answer not-found, the join is still refused, at the first reload, because NPM's `nginx -t` fails (`threat-model.md:302`). So yes: one proxy host forwarding to a disconnected container name blocks every new join while at least one proxy host is enabled. confirmed in code for the guard and the masking; medium, availability (it also blocks upgrades of NPM); the behaviours are stated at `threat-model.md:283` and `:302`, the missing detail is not.
- **An upgrade can finish "done" with nginx unable to start.** Where the resolver answers not-found, the upgrade's checks skip the unanswered name (`network_claims.go:1066`), the container is recreated, and nginx in the new container cannot load a static location whose name has no answer (inference; the harness saw `nginx -t` report `host not found in upstream`). `await` and `Verify` probe only NPM's API (`instance_upgrade.go:604-620`, `:962`), so the upgrade completes while every proxied site, a reserved exposure included, is down. An `operate` caller can produce it by stopping a forwarded container and upgrading. The spec's self-review said the upgrade would be refused up front in that case; the code does not do that. plausible; medium, availability; `threat-model.md:302` states the nginx behaviour, not that the upgrade proceeds.
- An attach cut off between the Engine's connect and `afterJoin` (agent restart, or a connect whose answer is lost, `effects.go:115-119`) leaves NPM joined with no held-address check and no second reload; applying the attach again finds NPM on the network and skips the guard and both reloads (`network_claims.go:317-323`), and the attach has no recovery handler. Spec R25 covers this re-entry for the undo of a detach only. plausible; low (no caller action cuts an apply off); `internal/modules/npm/network_claims.go:387-395`.
- `joinedProblem` reads NPM's endpoint by the network-name key and treats a missing endpoint as "holds nothing" rather than as a failed check (`internal/modules/npm/network_claims.go:875`); `networkEndpointOf` matches by network id. plausible; low.
- `threat-model.md:305` still says the proxy-host update against a running NPM of the pinned image was not run; w12f ran it in the harness (`w12e-evidence.md:324-326`). confirmed; low (an inaccurate sentence, in the cautious direction).
