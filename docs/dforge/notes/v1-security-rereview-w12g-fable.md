- Fix: `internal/modules/npm/network_claims.go:386-402` (attach) and `:825-846` (undo of a detach): reload, `joinGuard` (`:885-902`) re-reads the network and the targets and refuses before the connect, then `afterJoin` (`:908-939`) inspects NPM directly after the connect and disconnects on a hit (`leave`, `:998-1009`) before any reload, listing or lookup. - Regression tests: `TestW12gAttachMakesNoCallBetweenConnectAndInspection`, `internal/modules/npm/w12g_attach_test.go:106` — reproduces: yes; fails on revert: yes. `TestW12gAttachDisconnectsBeforeAnyLookupOrReload`, `w12g_attach_test.go:129` — reproduces: yes; fails on revert: yes. `TestA2_ForwardedAddressTakenAtConnectIsDroppedBeforeAnyReloadOrRead`, `w12g_security_followup_acceptance_test.go:247` — reproduces: yes (literal, name, undo); fails on revert: yes.

## Row 176: a forward name nginx still resolves to a freed address
- Verdict: CLOSED
- Attack path: a proxy host forwards to a Docker alias; the caller frees the alias's address A, detaches NPM and attaches it again at A, and nginx keeps the answer it resolved when it last loaded.
- Fix: `network_claims.go:876-881` (`reloadBeforeJoin`) and `:921-937` (second reload and the comparison with targets read afresh), on the exec reload of `nginx_exec.go:57-88`. A name with no answer in a custom location fails `nginx -t` and refuses before the connect (`nginx_reload.go:18-26`). Closes the path.
- Regression tests: `TestW12gAttachMakesNoCallBetweenConnectAndInspection` and `TestW12gAttachDisconnectsBeforeAnyLookupOrReload` (above) — reproduces: partly (they pin the order, not the stale-name scenario); fails on revert: yes. - Residual:
  - Traced the sibling "a name changes between the first reload and `joinGuard`'s read". For a Docker name it does not work: before the join nginx can only resolve the name on a network NPM is already on, so the answer is never an address of the network being joined (Docker DNS scope is inference), and a name with no answer fails `nginx -t`. For a DNS name the caller controls it works for the time from the connect to the second reload (at most `nginxReloadWait`, 10 s): the first check compares targets read after nginx loaded, so it misses the older answer. Confirmed in code; this is the owner-accepted DNS risk (spec D10, `threat-model.md:347`), and such a caller can re-point the name permanently anyway. The comment at `network_claims.go:1118-1121` ("nginx holds no older answer of the name than one read here") is wrong for that read; low.
  - Old workers finishing accepted requests: owner-accepted (`threat-model.md:299`).

## Row 190: the attach window
- Verdict: CLOSED
- Attack path: the caller frees a forwarded literal address or alias with a docker-lock action between the attach's guard and the connect; NPM takes it and nginx forwards to NPM's API until the disconnect, which the name lookups stretched to about 6 s.
- Fix: as row 1. `joinGuard` (`network_claims.go:885-902`) runs after the first reload; `afterJoin` compares at `:917-919` with only the inspection of `:909` between the connect and the disconnect; no `docker` key is taken (`:44,:57`).
- Regression tests: `TestW12gAttachRereadsTheNetworkAfterTheFirstReload`, `w12g_attach_test.go:166` — reproduces: yes; fails on revert: yes. `TestW12gAttachMakesNoCallBetweenConnectAndInspection`, `:106` — yes; yes. `TestW12gUndoOfADetachChecksInTheSameOrder`, `:367` — yes (both halves); yes. `TestA3_AddressFreedAfterTheFirstReloadRefusesBeforeTheConnect`, `w12g_security_followup_acceptance_test.go:300`, and `TestA19_AFreedAddressNeverLeavesNPMOnTheNetworkWhoeverFreedIt`, `:1339` — yes; yes.
- Residual:
  - The interval from the connect to the disconnect, repeatable by retrying. Confirmed; medium; owner-accepted yes (U2, `threat-model.md:298`).
  - `joinGuard` reads the network first (`:886`) and the targets afterwards (`:890`), so a proxy-host listing and a lookup pass of up to 6 s sit between the network re-read and the connect; `TestA1` pins that order (`w12g_security_followup_acceptance_test.go:230`). A caller with a slow-answering name gets seconds, not milliseconds, to free the address after the re-read, so the refusal before the connect is easy to pass. Spec D1 describes the other order (targets, then the network). The outcome is still the U2 interval. Confirmed; low; covered by U2's wording ("can repeat it by retrying").
  - "At most 10 seconds" (`threat-model.md:298`) is not what the code bounds: the inspection at `:909` runs under the apply's context (45 s), only the disconnect has the 10 s bound (`:1002`), and a failed disconnect leaves NPM there until repair. It needs a slow Engine, which a caller cannot cause: the apply's context is detached from the request (`internal/core/lifecycle/apply.go:78`). Confirmed; low; not recorded.
  - `lostJoin` returns the connect error when its one inspection fails or shows NPM not yet on the network (`:947-949`). If the Engine finishes the connect afterwards (inference), NPM is joined unchecked, the change is `needs_repair` and keeps the `npm` lock (`lifecycle/settle.go:42-46,93-101`), and no reconcile pass runs until the repair. Plausible; low (Engine fault, not caller-controlled); the lock limit is in U3, the case is not recorded.
