# Security review — Fable

Repository `/root/repositories/darkpanel`, branch `main`, commit `dc91aa2`. Read-only review against `docs/security/threat-model.md`; register rows cite the `#` column of `docs/dforge/registers/2026-10-21-v1-completion.md`.

## Findings

### F1: An `operate` user can publish NPM's backend API (port 3000) through `npm.proxyhost.add`, bypassing the admin-only `npm.admin.expose`
- Severity: high
- Confidence: confirmed
- Area: Exposure
- Location: `internal/modules/npm/proxy/upstream.go:38-59` (only `npmAdminPort = 81` is reserved, lines 15 and 47); `internal/modules/npm/proxyhost_add.go:43-50` (agent-side `ClassCompensable`, no `MinScope`, so `core.DefaultScope` at `internal/core/scope.go:10-11` gives `operate`); `internal/modules/npm/composite_admin.go:14-18` (controller-side composite, so `DefaultScope` gives `admin`); `internal/modules/npm/proxy/location.go:15-29`
- Prior row: 330 (state `open`, severity `minor`). The row calls the bind address of port 3000 "unverified (inference)". It is now verified: upstream `backend/index.js` on the NginxProxyManager `develop` branch runs `const server = app.listen(3000, () => {` with no host argument, so Node binds every interface of the container. The recorded severity `minor` is wrong: this is a lower scope reaching an admin effect.
- Description: `CheckUpstream` refuses an upstream at NPM's own names or addresses only when `port == npmAdminPort` (81). NPM's backend, which serves the whole admin REST API including `POST /api/tokens` (login) and every proxy-host, certificate and user operation, listens on 3000 inside the container on all interfaces. A proxy host whose forward host is `darkpanel-npm` (or any address in `r.NPMAddrs`) and whose forward port is 3000 passes the reserved check. Docker's embedded DNS resolves a container's own name on a user-defined network, so nginx inside the NPM container proxies the public hostname straight to its own backend. Publishing NPM's admin surface is otherwise reachable only through `npm.admin.expose`, which needs `admin` and drives the every-page banner; `npm.proxyhost.add` needs `operate`.
- Failure scenario: an `operate` token holder (or a stolen `operate` credential) calls `POST /api/v1/hosts/{host}/actions/npm.proxyhost.add/1/plan` then `apply` with `{"domains":["npm.attacker.example"],"forwardScheme":"http","forwardHost":"darkpanel-npm","forwardPort":3000}` and a certificate id. NPM's full admin API is now on the internet at that hostname with no Darkpanel warning banner (the banner is driven by `npm.admin.expose` state), reachable for credential guessing, for any NPM API vulnerability, and for the operator's stolen NPM credentials. The pinned image tag (`internal/modules/npm/image.go`) was not diffed against `develop`, but `app.listen(3000)` without a host has been NPM's shape for years.
- Fix: in `CheckUpstream`, outside `adminOwner` refuse every port of `r.NPMAddrs`, `r.NPMNames` and `npmContainerName` (not only 81), as row 330 proposes; keep the `adminOwner` exception for port 81 only. Add table rows in `upstream_test.go` for `darkpanel-npm:3000` and `<npm addr>:3000` under a non-admin parent, and run the same check in `npm.proxyhost.edit`.

### F2: A forward host name that resolves to loopback, NPM's address or the panel gateway passes the reserved check
- Severity: high
- Confidence: confirmed
- Area: Exposure
- Location: `internal/modules/npm/proxy/upstream.go:38-59, 65-73, 177-193` (names are compared only against the loopback names and NPM's own names; nothing is resolved); `internal/modules/npm/proxyhost_add.go:37, 87-101, 258-296` (`proxyhostAddHostName` admits any DNS name; `checkUpstream` adds NPM's names and addresses but resolves nothing)
- Prior row: 326 (state `open`, severity `Important`). Recorded state and severity are right; this report confirms the path and grades it `high` under the brief's rubric.
- Description: nginx inside the NPM container resolves a static `proxy_pass` host through the container's resolver, which Docker's embedded DNS forwards to the host's upstream DNS for any name it does not own. `CheckUpstream` only tests a name against `loopbackNames` and `r.NPMNames`. A name the caller controls in public DNS (an `A` record `npm-admin.attacker.example -> 127.0.0.1`) is therefore accepted with port 81, and nginx proxies to its own admin UI. The same trick with an `A` record for the NPM container's address, or for the panel gateway in `PanelRange`, passes the `isNPMAddr` and `inNetwork`/`isGateway` branches, which only run when `isAddr`.
- Failure scenario: an `operate` user creates a proxy host with `forwardHost: npm-admin.attacker.example`, `forwardPort: 81`. NPM's admin UI (port 81, login page and full UI, not only the API of F1) is published on a hostname of the attacker's choosing without `npm.admin.expose`, without `admin` scope and without the banner. Against the panel gateway the effect is smaller: the runtime listener still accepts only NPM as peer and `proxiedOrigin` refuses unsafe requests whose `Origin` is not the recorded public host (`internal/controller/api/server.go:348-358`), so a second hostname serves the panel's pages and `GET`s but not a login; still a bypass of `panel.exposure.add`.
- Fix: resolve every forward host that is not an IP literal at plan time and again at apply time with the host's resolver (`net.DefaultResolver.LookupNetIP`) and run the address branch of `CheckUpstream` on every answer; refuse a name with no answer or whose answers differ between plan and apply. Alternatively, and simpler, admit as names only the container names and network aliases Docker's embedded DNS answers on NPM's networks (the set `npm.network.attach` and the composites already use) plus IP literals. Apply the same rule in `npm.proxyhost.edit` and add the loopback-resolving harness case row 326 asks for.

### F3: Any unauthenticated client can lock out a known username indefinitely
- Severity: medium
- Confidence: confirmed
- Area: Authentication
- Location: `internal/controller/auth/ratelimit.go:14-20, 140-148, 182-199`; `internal/controller/auth/login.go:66-72, 107-116`
- Prior row: none for this effect (row 174, `deferred`, covers the neighbouring case of one client behind a proxy exhausting the per-source limit).
- Description: `fail` records a failure under both `u:<username>` and `s:<source>`; `UsernameFailureLimit` is 5 within 15 minutes and the lock lasts 15 minutes. The username key is independent of the source, so five wrong passwords for `admin` from anywhere lock `admin` for everyone, and repeating them every 15 minutes keeps it locked. Usernames are not secret. The login route is public on every listener, including runtime listeners of an exposure.
- Failure scenario: with the panel exposed through NPM or a tunnel, an internet attacker sends five `POST /api/v1/auth/login` bodies with `{"username":"admin","password":"x","code":"000000"}` every 14 minutes from rotating addresses. The administrator cannot log in through the web UI for as long as the attacker keeps going; combined with a pending firewall change this can also prevent a confirm. The controller socket and API tokens are unaffected, which bounds the impact to the browser path.
- Fix: keep the per-source lock, and turn the per-username counter into a slowdown instead of a refusal (a delay that doubles per failure up to a few seconds, applied inside the hashing slot), or key the lock on `(username, source /64)`; optionally exempt loopback and tailnet sources from the username lock. Record the choice in the threat model's residual list either way.

### F4: `derp.node.probe` lets a `read` user use any agent as a TLS and STUN scanner of private networks and receive raw TLS error text
- Severity: medium
- Confidence: confirmed
- Area: DERP host
- Location: `internal/modules/derp/node_probe.go:28-35` (`core.DefineRead`, so `read` scope by `internal/core/scope.go:8-9`), `:70-97, 106-112` (only loopback, unspecified, multicast and link-local are refused), `:162-196` (names are resolved and probed), `:264-280` (`err.Error()` is returned to the caller); ports fixed at 443 and 3478 by `internal/modules/derp/server/server.go:45-47`
- Prior row: 306 (state `open`, `minor`). The row is accurate; this report grades it `medium` because the actor is the lowest scope and the output names internal hosts.
- Description: the probe takes any IP literal or DNS name, resolves it and makes the agent open a TLS connection to port 443 and send a STUN binding to 3478, then returns the Go TLS error verbatim. RFC 1918, CGNAT (100.64/10) and ULA ranges are accepted, so a `read` user maps which private hosts answer on 443, reads certificate subject names from failed verifications, and learns which hosts have STUN open. Darkpanel's own DERP servers are public in the documented topology, so nothing legitimate needs those ranges.
- Failure scenario: a `read` token holder calls `POST /api/v1/hosts/{host}/actions/derp.node.probe/1/read` with `{"hostName":"10.0.0.1"}`, then iterates addresses; each answer's `tls.error` text names the internal certificate (`x509: certificate is valid for intranet.corp.example, not 10.0.0.1`), giving a reconnaissance oracle from inside the network.
- Fix: refuse `10/8`, `172.16/12`, `192.168/16`, `100.64/10`, `fc00::/7` and IPv4-mapped forms in `nodeProbeAllowedAddr` and among resolved answers; raise the action's `MinScope` to `operate`; map probe errors to a fixed vocabulary (`timeout`, `refused`, `tls_verify_failed`, `pin_mismatch`, `stun_no_answer`) and log the detail on the agent instead of returning it.

### F5: Containers on a network NPM joined reach NPM's admin login on 81 and its API on 3000
- Severity: low
- Confidence: confirmed
- Area: Exposure
- Location: `internal/modules/npm/network_claims.go:24-30` (`npm.network.attach` joins the NPM container to a target's network); `internal/modules/npm/instance_deploy.go:265-272` (admin password is 32 random bytes, base64url)
- Prior row: 329 (state `open`, `minor`). Accurate; this report grades it `low` and recommends accepting it.
- Description: inside the container nginx serves the admin UI on 81 and the backend on 3000 on every interface; only the host-side publish is loopback. Every container on a network joined through `npm.network.attach` therefore reaches NPM's admin login. The password is 256 bits of randomness, so guessing is infeasible; the exposure is to NPM's own authentication code and any vulnerability in it.
- Failure scenario: a compromised workload container on an attached network connects to `darkpanel-npm:81` or `:3000`; with NPM's generated password it gets nowhere, but an unauthenticated NPM vulnerability would be reachable from inside the host's Docker networks.
- Fix: accept for v1 and record it in the threat model as accepted with the password-entropy reasoning; revisit if the pinned NPM image gains a way to bind 81 and 3000 to loopback or to carry an `allow 127.0.0.1; deny all;` for the admin server.

### F6: Label digests in Docker network and volume effect documents are unsalted, and plan diffs show raw label values
- Severity: low
- Confidence: confirmed
- Area: Secret handling and delivery
- Location: `internal/modules/docker/dstate/object.go:57-72, 93, 111`; `internal/modules/docker/network_manage.go` (plan diff, per row 384)
- Prior row: 384 (state `open`, `minor`). Accurate.
- Description: label values are replaced by `SHA-256(value)` in the effect document so an observation can compare them without storing them. Label values are low-entropy, so anyone who reads effects can confirm a guessed value by hashing it. The same audience (`read`, through `GET /api/v1/changes/{id}` and `/effects`) sees the raw values in the plan diff, so the digest protects nothing today. Labels are rarely secrets, hence `low`.
- Failure scenario: a `read` user guesses a label such as `billing-tier=enterprise` from the digest; the plan diff shows it anyway.
- Fix: either keep digests and make them keyed, `HMAC-SHA256(salt, value)` with a random 16-byte `salt` stored in the document (observations recompute with the stored salt), and show only label keys in the diff; or drop the pretence, record the values and document that labels are not secrets.

### F7: `golang.org/x/crypto@v0.58.0` carries GO-2026-5932 in a package Darkpanel does not import
- Severity: low
- Confidence: confirmed
- Area: Update path (dependency hygiene)
- Location: `go.mod:17`; no Go file under `cmd/`, `internal/`, `release/` or `test/` imports `openpgp` (grep over `**/*.go`); `internal/modules/tailscale` parses keyrings with its own `keyringFingerprints`
- Prior row: 429 (state `open`). Accurate.
- Description: the advisory is against the unmaintained `openpgp` package of the module. Darkpanel's symbol graph never reaches it, so no code path is affected; the only cost is a `govulncheck` report until a tagged `x/crypto` release carries the fix.
- Failure scenario: none exploitable; a future import of `openpgp` by a dependency would reopen the question.
- Fix: accept; keep row 429 open as a tracking item and move to the next tagged `x/crypto` release. A `scripts/` check that `go list -deps` never includes `golang.org/x/crypto/openpgp` would keep the accepted state honest.

### F8: Unsafe cookie-session requests through a runtime listener are accepted without an `Origin` header
- Severity: low
- Confidence: confirmed
- Area: Authentication
- Location: `internal/controller/api/server.go:348-358` (`proxiedOrigin` returns nil when `len(origin) == 0`), `:335-338` (CSRF header check), `internal/controller/api/auth.go:30-40` (`SameSite=Strict`, `HttpOnly`, `__Host-` on HTTPS)
- Prior row: 245 (state `open`). Accurate.
- Description: the session cookie is `SameSite=Strict` and `HttpOnly`, and every unsafe session request must carry `X-CSRF-Token`, an HMAC of the session id under a key derived from the controller key (`internal/controller/auth/session.go:186-201`). A cross-site browser request carries neither; a non-browser client that holds both can set any `Origin`. Requiring `Origin` adds no attacker that the two existing checks let through.
- Failure scenario: none beyond what a stolen session plus CSRF token already allows, which the threat model lists as residual.
- Fix: accept and record the reasoning. Optional hardening with no compatibility cost: when `Sec-Fetch-Site` is present and is neither `same-origin` nor `none`, refuse the unsafe request.

### F9: Threat-model claim about ufw argument protection names the wrong mechanism for `comment`
- Severity: low
- Confidence: confirmed
- Area: Command execution
- Location: `docs/security/threat-model.md:131`; `internal/modules/firewall/model/rule.go:103, 133` (`commentPattern` is `^[A-Za-z0-9 :._/-]{0,64}$`, which admits a leading `-`); `internal/modules/firewall/model/args.go:106-118` (`withComment` prefixes a Darkpanel rule's comment with `darkpanel:<id>` and drops a manual comment starting with `-`); `internal/modules/firewall/actions_rule.go:54-71` (`newRule` refuses `origin: manual` in input); `internal/platform/exec_rules.go:135-143` (`execMatchUfw` admits any arguments after the verb)
- Prior row: none
- Description: the threat model says "the input schema patterns refuse a value that starts with `-`". For `from`, `to`, ports and interfaces that is true. For `comment` it is not; what keeps `-foo` out of the `ufw` argument vector is that every rule a client adds is a Darkpanel rule whose comment argument is `darkpanel:<ULID> <label>`, and that `withComment` drops a manual comment with a leading `-`. The outcome is safe; the stated reason is not the operative one, and a future change that lets a client write a manual comment would silently lose the protection.
- Failure scenario: none today.
- Fix: either tighten `commentPattern` to `^$|^[A-Za-z0-9][A-Za-z0-9 :._/-]{0,63}$` so the claim becomes true, or reword the threat model to name `withComment` and the tag prefix.

### F10: The global enrollment budget can be exhausted by any client that reaches the agent listener
- Severity: low
- Confidence: confirmed
- Area: Agent protocol
- Location: `internal/controller/fleet/tokens_limit.go:14-19, 41-52` (`EnrollGlobal = 60` per minute across all sources); `internal/controller/fleet/enroll.go:51-56` (the limit is applied before the path or token is read); `internal/controller/listen/agent.go:19-73` (loopback, every Tailscale address and `--agent-listen` extras)
- Prior row: none
- Description: sixty admitted enrollment requests per minute from any mix of sources block every further enrollment for the rest of the minute, and the attacker can keep it full. The listener is on the tailnet by design, so the actor is anyone on the tailnet, not the internet. Impact is availability of enrollment only; tokens expire after an hour (`fleet/tokens.go:19`), so a sustained flood forces reissue.
- Failure scenario: a tailnet peer sends sixty `POST /enroll/v1` requests per minute with junk tokens; a new host's `darkpanel agent enroll` answers `enroll.rate_limited` until the flood stops.
- Fix: accept for v1 (tailnet-local, availability only), or make the global limit soft and log the top sources so the operator can see who is flooding.

## Known residual risks
- `Origin`: accept — the cookie is `SameSite=Strict` and `HttpOnly` and every unsafe session request needs the HMAC CSRF header, so a cross-site browser request carries neither credential, and a non-browser holder of both can forge `Origin` anyway; record this in the threat model and, optionally, refuse an unsafe request whose `Sec-Fetch-Site` is present and neither `same-origin` nor `none` (`internal/controller/api/server.go:348-358`) — severity if unfixed: low
- `RFC 1918`: fix — in `nodeProbeAllowedAddr` and `nodeProbeResolve` refuse `10/8`, `172.16/12`, `192.168/16`, `100.64/10`, `fc00::/7` (after `Unmap`), raise `derp.node.probe` to `MinScope: operate`, and replace `err.Error()` in `nodeProbeResult` with a fixed vocabulary while logging the detail on the agent (`internal/modules/derp/node_probe.go:28-35, 106-112, 174-189, 275-280`) — severity if unfixed: medium (F4)
- `forward host`: fix — resolve every non-literal forward host at plan and at apply with the host's resolver and run the address checks on every answer, refusing a name with no answer or with answers that changed between plan and apply; or restrict names to the container names and aliases on NPM's networks plus IP literals; apply the same in `npm.proxyhost.edit` and add the loopback-resolving harness case (`internal/modules/npm/proxy/upstream.go:38-73`, `internal/modules/npm/proxyhost_add.go:87-101, 258-296`) — severity if unfixed: high (F2)
- `port 81`: accept — inside the container 81 cannot be rebound without changing the pinned image; the only credential behind it is 32 random bytes generated at deploy (`internal/modules/npm/instance_deploy.go:265-272`), so a joined container gains an authentication surface and nothing more; document it as accepted next to row 329 and note that F1's fix closes the public-exposure half of the same surface — severity if unfixed: low (F5)
- `port 3000`: fix — verified against upstream `backend/index.js` (`app.listen(3000)` with no host, so every interface); reserve every port of NPM's own names and addresses outside the `npm.admin.expose` parent in `CheckUpstream` (`internal/modules/npm/proxy/upstream.go:47`), and confirm the pinned image tag in `internal/modules/npm/image.go` has the same `listen` call — severity if unfixed: high (F1)
- `digest`: fix, cheaply — store a random 16-byte salt in the effect document and record `HMAC-SHA256(salt, value)` per label, recomputing with the stored salt on observation, and print only label keys in the network and volume plan diffs (`internal/modules/docker/dstate/object.go:57-72`, `internal/modules/docker/network_manage.go`); or accept by declaring labels non-secret and dropping the digest — severity if unfixed: low (F6)
- `openpgp`: accept — no Go file imports `openpgp` and `keyringFingerprints` is Darkpanel's own parser, so the advisory has no reachable code; keep row 429 open until a tagged `x/crypto` release carries the fix, and add a dependency-graph check so the accepted state cannot silently change — severity if unfixed: low (F7)
